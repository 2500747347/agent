# 01 需求与架构设计

> 项目：个人AI助理 Agent（Personal AI Assistant Agent）
> 定位：从零手写 Agent 核心的一次完整开发实践，不依赖现成 Agent 框架。

---

## 1. 项目背景与目标

### 1.1 背景

当前主流 Agent 产品（如各类 AI 助理、Copilot）
的底层能力 = **大模型 + 工具调用 + 记忆 + 规划**。本项目的核心价值在于：

- 亲手实现 Agent 内核（ReAct 循环、Function Calling、工具注册、记忆），理解每个环节的原理；
- 交付一个可本地运行、可演示、可评测的完整应用。

### 1.2 目标

| 编号 | 目标 | 验收方式 |
|---|---|---|
| G1 | 手写 Agent 内核，不依赖 LangChain/LangGraph 等框架 | 代码评审：核心循环自研 |
| G2 | 支持 5+ 种工具调用（时间/计算/待办/笔记/搜索/天气） | 功能演示 |
| G3 | 支持多轮会话记忆与跨会话长期记忆 | 功能演示 + 单测 |
| G4 | 可配置模型（Codex/GPT/DeepSeek/通义等），无 Key 可 Mock 运行 | 配置切换演示 |
| G5 | 建立评测体系，工具调用准确率 ≥ 85% | 评测脚本输出指标 |

## 3. 系统架构

### 3.1 总体分层

```
┌──────────────────────────────────────────────────────────────┐
│ 交互层  ui/app.py（Gradio Web 界面，多轮对话 + 过程可视化）      │
├──────────────────────────────────────────────────────────────┤
│ Agent层  agent/core.py（ReAct 主循环，意图→工具→回复）          │
│          agent/llm.py（LLM统一封装：Codex/GPT/…/Mock）         │
│          agent/tools.py（工具注册表 + 调度）                    │
│          agent/memory.py（会话记忆 + 长期记忆管理）             │
├──────────────────────────────────────────────────────────────┤
│ 工具层  tools/（时间/计算/待办/笔记/搜索/天气，各自独立模块）     │
├──────────────────────────────────────────────────────────────┤
│ 数据层  data/（SQLite：待办、笔记、长期记忆库；配置：config/）   │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 核心数据流（一次对话的完整处理）

```
用户输入
   │
   ▼
LLM 调用（带可用工具 schema + 会话历史）
   │
   ├─ 无工具调用 → 直接生成回复 → 返回用户
   │
   └─ 有工具调用（name + arguments）
          │
          ▼
     工具注册表查找 → 校验参数 → 执行工具
          │
          ▼
     工具结果(Observation) 追加到消息历史
          │
          ▼
     再次调用 LLM（最多 N 轮循环，默认 5）
          │
          └─ 直到 LLM 不再调用工具 → 生成最终回复
```

### 3.3 模块职责

| 模块 | 文件 | 职责 | 关键接口 |
|---|---|---|---|
| 主循环 | `agent/core.py` | ReAct 循环控制、轮次上限、错误兜底 | `Agent.run(user_input) -> str` |
| LLM 封装 | `agent/llm.py` | 统一 chat/tool-calling 接口、Mock 实现 | `LLM.chat(messages, tools) -> response` |
| 工具注册 | `agent/tools.py` | 注册表、schema 生成、参数校验 | `@tool` 装饰器、`ToolRegistry` |
| 记忆 | `agent/memory.py` | 会话历史窗口、长期记忆读写 | `Memory`、`LongTermMemory` |
| 工具 | `tools/*.py` | 各工具的具体实现与 schema | 纯函数 + 类型注解 |
| 界面 | `ui/app.py` | Gradio 对话界面、过程可视化 | `main()` |
| 评测 | `eval/run_eval.py` | 测试集执行、指标统计 | `run_eval() -> report` |

## 4. Agent 核心机制设计

### 4.1 ReAct 推理循环

采用 **工具调用式 ReAct**（非文本解析式）：LLM 通过原生 `tool_calls` 结构化输出
`name + arguments`，内核执行后把结果作为 observation 回填，循环直至收敛。

```
循环（最大 5 轮）：
  messages.append(user_input 或 tool_result)
  resp = llm.chat(messages, tools)
  if resp.tool_calls:
      for each call:
          tool = registry.get(call.name)
          result = tool(**call.arguments)
          messages.append({role: "tool", content: result})
  else:
      return resp.content   # 最终回复
```

**为什么不用纯文本解析**：LLM 输出工具调用时，JSON 解析失败率高、不稳定；
原生 Function Calling 由模型保证结构化输出，工程上更可靠，也是主流 Agent 产品的做法。

### 4.2 工具注册机制

```python
@tool("get_current_time", "获取当前日期与时间")
def get_current_time() -> str:
    """返回今天的日期与星期"""
    return datetime.now().strftime("%Y-%m-%d %A")
```

- 装饰器自动收集：函数 docstring → 工具描述，类型注解 → 参数 schema；
- 注册表自动生成 OpenAI 兼容的 `tools` 列表；
- **新增工具零侵入**：写一个函数 + 一个装饰器即可，内核无需改动。

### 4.3 记忆设计

| 类型 | 机制 | 存储 | 说明 |
|---|---|---|---|
| 会话记忆 | 滑动窗口（保留最近 N 轮） | 内存（本轮） | 维持多轮上下文，防超长 |
| 长期记忆 | 抽取式存储：用户主动告知的偏好/事实，写入库，检索时召回 | SQLite（`data/memory.db`） | 跨会话可用，支持“我上次说的…”类提问 |

长期记忆设计原则：
- **显式记忆为主**：用户明确说“记住/我的XX是”时写入，避免幻觉性记忆；
- 检索采用关键词/向量相似度（P3 落地，向量维度小，可自实现）。

## 5. 技术选型与论证

| 项 | 选型 | 备选 | 理由 |
|---|---|---|---|
| 语言 | Python 3.13 | 3.10/3.11 | 已装，生态成熟 |
| LLM SDK | openai（v3.x） | httpx 直连 | 官方维护，统一兼容各模型 |
| LLM 模型 | Codex（用户持有） | DeepSeek/通义/智谱 | OpenAI 兼容接口，config 可切 |
| 界面 | Gradio 6.x | Streamlit | 对话组件成熟，工具过程展示方便 |
| 存储 | SQLite（标准库） | JSON 文件 | 零依赖、单文件、可跨会话 |
| 检索 | 自实现（numpy 余弦相似度） | ChromaDB | 语料小（<100 条），自实现可讲原理且规避 3.13 兼容风险 |
| 评测 | 自写脚本 + 测试集 JSON | pytest 集成 | 指标口径可控，可量化对比 |

### 5.1 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| openai 3.x API 与 1.x 差异 | 封装报错 | P2 先验证 API 签名，封装层隔离 |
| 无有效 API Key | 无法真实调用 | Mock 模式先行，config 一键切换 |
| LLM 工具参数幻觉（传错参数） | 工具执行报错 | 注册表参数校验 + 错误信息回填给 LLM 自纠 |
| 无限循环 | 卡死 | 轮次上限（5 轮）强制退出 |
